## Scope for this phase

1. Implement `crates/baa-render`: polygon tessellation via `lyon`
   (converting each `baa-ir` `Polygon` into a triangle mesh), a `wgpu`
   render pipeline that draws the tessellated silhouette against a
   configurable background, and the headless framebuffer readback path
   that produces CPU-side raw frame buffers for the encoder (phase 5's
   scope, not this phase's, but the readback interface needs to exist and
   be tested independently here).
2. Implement the background styles described in `docs/03_SDD.md` section
   5: at minimum a solid color and the procedural gradient-plus-moon-plus-
   petals scene established during earlier prototyping. This is original
   procedural artwork generated by this crate's own code, not extracted
   from any source video; keep it that way.
3. Implement the mandatory software rasterizer fallback per
   `docs/adr/ADR-0003-rendering-backend-wgpu.md`: automatically selected
   when `wgpu` cannot acquire a suitable adapter at startup, with a
   warning-level log emitted every time this path is taken, never
   silently. This is a hard requirement, not an optional stretch goal for
   this phase, because CI (per `docs/06_QA_TEST_PLAN.md` section 2) has no
   GPU and depends on this path existing and being correct.
4. Implement `RenderConfig` (resolution, output fps, background style,
   fill color, anti-aliasing level) per `docs/03_SDD.md` section 3.2, and
   frame resampling by nearest-timestamp against the BSF's `t_ms` field
   when output fps differs from source fps.
5. Write the unit tests listed in `docs/06_QA_TEST_PLAN.md` section 3.2:
   `test_tessellation_triangle_count_matches_polygon_complexity`,
   `test_software_rasterizer_fallback_selected_without_gpu_adapter`,
   `test_render_respects_output_resolution_config`,
   `test_render_frame_resampling_when_output_fps_differs_from_source`.
6. Set up the golden-frame regression test infrastructure per
   `docs/06_QA_TEST_PLAN.md` section 5: render a small, fixed set of
   representative frames from phase 3's fixture BSF file, store the
   reference PNGs in the test fixtures directory, and write
   `test_render_matches_golden_frame_ssim` with the SSIM >= 0.98 threshold
   specified there. Run this test against both the GPU path (if available
   in your development environment) and the software fallback path, and
   confirm both independently meet the threshold, since
   `docs/adr/ADR-0003-rendering-backend-wgpu.md` explicitly calls out that
   keeping both paths correct and in sync is a real cost this test exists
   to manage.

## Test gating for this phase

Follow `.agents/rules/02-test-gating.md` in full. Run `cargo test -p
baa-render` and confirm all tests above pass, including confirming the
software fallback path is actually exercised in the CI-equivalent
environment (no GPU) you are testing in, not merely that the code for it
exists and compiles.

## Benchmarking for this phase

This phase's code is on both render throughput benchmark paths
(`docs/02_TRD.md` section 6: `bench_render_throughput` at 960x540
headless, target >= 300fps, and `bench_render_throughput_1080p` at
1920x1080 on GPU, target >= 60fps). Follow
`.agents/rules/04-benchmark-recording.md`: write both Criterion
benchmarks against phase 3's fixture BSF file, run them, and run
`harness/benchmark_update.py`. If you are developing in an environment
without a suitable GPU, state this plainly in the phase summary and in
the pull request description rather than fabricating or estimating the
1920x1080 GPU figure; record only what you actually measured, and flag
the GPU-path benchmark as needing to be run by the project owner locally
before phase 6's release gate, consistent with
`docs/06_QA_TEST_PLAN.md` section 2's statement that CI itself cannot
exercise the GPU path.
