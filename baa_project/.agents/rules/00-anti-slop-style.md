# Rule: writing style for code, comments, commits, and documentation

This rule applies to every piece of written output in this repository:
code comments, docstrings, commit messages, pull request descriptions,
and any document under `docs/`. It exists because generic AI-generated
prose has a recognizable set of habits that make technical writing worse,
not better, and this project's documentation is meant to be read and
trusted as a real specification, not skimmed past as filler.

I am not aware of a single standardized name or numeric code for this
style requirement. If one exists and you encounter it, follow it and
note that you did so. In the absence of that, follow the concrete rules
below, which are enforceable and checkable, unlike a vague instruction to
"sound more human."

## Hard rules

- No emoji, anywhere, in any file this project controls.
- No em dashes. Use a period, a comma, or restructure the sentence.
- No rhetorical questions used as a paragraph opener ("But what does this
  mean in practice?").
- No throat-clearing openers ("It's worth noting that...", "In today's
  fast-paced development landscape...", "Let's dive in").
- No false-summary closers that restate what was just said in slightly
  different words ("In conclusion, this approach provides a robust and
  scalable solution.").
- No unearned intensifiers: avoid "robust," "seamless," "powerful,"
  "comprehensive," "cutting-edge," "state-of-the-art," "battle-tested,"
  unless a specific claim immediately follows that actually justifies the
  word (a number, a test name, a citation to a doc section). If the
  sentence works with the word deleted, delete it.
- No padding a list of three when two items are true and a third is
  invented to complete a pattern.
- Do not restate the obvious content of the code in a comment ("increment
  i by one"). A comment earns its place by explaining why, not what,
  unless the what is genuinely non-obvious.
- Prefer concrete claims over vague ones. "Reduces peak memory from 1.8GB
  to 400MB on the 5-minute fixture" beats "significantly improves memory
  usage."
- Prefer active voice and direct statements. Say what is true, not what
  "can be considered to potentially" be true.
- Vary sentence length naturally the way a person writing carefully
  would, rather than producing uniform medium-length sentences in a row.
  This is a byproduct of writing to actually explain something precisely,
  not a separate thing to perform.

## Commit messages and pull request descriptions

Follow the Conventional Commits format defined in
`.agents/rules/01-git-workflow.md` for the summary line. The body, when
present, states what changed and why in plain declarative sentences. It
does not restate the diff line by line, and it does not include a
"Generated by" or agent-attribution footer of any kind.

## Documentation updates

When updating a document under `docs/` at the end of a phase (per
`.agents/rules/03-documentation-update.md`), match the existing
document's voice: direct, technical, willing to state a limitation
plainly instead of euphemizing it (see, for example, how
`docs/adr/ADR-0004-matting-strategy-pluggable-backend.md` states the
temporal-median approach's limitations without hedging). Do not soften an
honest "this does not work for X" into "this may have some limitations
in certain scenarios."

## Self-check before finishing any written output

Before treating a piece of writing as final, reread it and ask
specifically: does any sentence here say something without saying
anything, would a domain expert reading this flinch at any specific
phrase, and is every superlative or intensifier backed by a fact stated
nearby. If the answer to any of those is uncomfortable, rewrite the
sentence rather than leaving it.
